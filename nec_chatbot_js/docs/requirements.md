# RAGシステム（JavaScript版）要件定義書

プロジェクト名: サークル書類・マニュアル RAGシステム（nec_chatbot_js）
作成日: 2026-06-16
位置づけ: Python版（nec_chatbot）の機能を JavaScript / Node.js へ移植し、ラズパイ常時稼働とWeb公開（学外含む）に最適化した版

---

## 1. 概要・目的

サークルの書類・マニュアル（PDF）に自然言語で質問でき、出典（ファイル名・ページ）を明示してハルシネーションを抑えるRAGシステム。Python版で作り込んだ検索品質（ハイブリッド検索・用語注入・係名ブースト・文脈整形）をそのまま JavaScript で再実装し、ラズパイ上で常時稼働するWebアプリとして提供する。

### 移行の背景（なぜJS化するか）
- ラズパイでの常時稼働を見据え、環境構築・保守運用コストを下げる
- Python（PyTorch・Chroma）依存を減らし、Node 単一ランタイムに寄せる
- 最終的にブラウザからアクセスできるWebページとして公開する（学外からも）

---

## 2. オフラインの範囲（重要な前提）

回答生成は Gemini API を継続使用するため、正確には次の切り分けとなる（完全オフラインではない）。

| 処理 | 実行場所 | オフライン |
|------|----------|-----------|
| 文書の取り込み・索引構築 | ラズパイ内（ローカル） | ○ |
| 埋め込み（ベクトル化） | ラズパイ内（ローカルモデル） | ○ |
| 検索（ベクトル＋BM25＋RRF＋ブースト＋用語注入） | ラズパイ内（ローカル） | ○ |
| 回答生成 | Gemini API | ×（要ネット） |

プライバシー方針はPython版を踏襲する。PDF全文はラズパイ内に保持し、APIへ送るのは質問文＋検索で選ばれた断片のみ。

将来の完全オフライン化の余地: 生成部は差し替え可能なインターフェース（Generator）として設計する。これにより、将来ローカルLLMや抽出型（LLMなし）に切り替えられる余地を残す。

---

## 3. 利用者と利用シーン

- 対象: サークル員 10〜50人（段階的に拡大）
- 接続方法: 学内外のスマホ/PCのブラウザからアクセス。ラズパイは大学WiFi経由で外部公開する
- 公開手段: ポート開放はせず、Tailscale Funnel / Cloudflare Tunnel 等で安全に外部へ出す想定
- 想定負荷: 初期は月間クエリ少なめ。低トラフィック前提（高速化は優先度低）

## 4. 機能要件

### 4.1 検索・回答（Python版からの全機能を移植）

| 機能 | 説明 |
|------|------|
| 文書取り込み | PDF からテキスト抽出。画像PDFは手起こしの Markdown(.md) で差し替え（同名 .md 優先） |
| チャンク分割 | PDFは固定長（500字・オーバーラップ50）、.mdは見出し（#）単位。空白正規化・薄いチャンク除外・係名ヘッダー付与 |
| ローカル埋め込み | 多言語MiniLMをローカル実行してベクトル化 |
| ベクトル検索 | 全チャンクとのコサイン類似度（総当り） |
| 語彙検索（BM25） | 形態素解析＋用語保護層で分かち書きし、BM25でスコアリング |
| ハイブリッド統合 | ベクトルとBM25の順位を RRF で統合 |
| 用語注入 | 質問に含まれる内輪語の定義を用語辞典から引き、検索クエリへ連結 |
| 係名一致ブースト | 質問の係名がチャンクの出典ファイル名に一致したら順位を加点 |
| 文脈整形 | 同一文書をまとめ文書順に並べ、隣接チャンクを結合し、ヘッダー重複を整理してAIへ渡す |
| 回答生成 | Gemini API（gemini-2.5-flash、思考無効化）で回答。差し替え可能な Generator 経由 |
| 出典表示 | 回答に「ファイル名・ページ」を明示 |
| 索引再構築 | 文書追加後、管理者がコマンドで再索引 |
| 評価 | 質問→期待出典の評価セットで Hit@k・MRR を計測（保守用） |

### 4.2 Webインターフェース（新規・Alpine.js）

| 機能 | 説明 |
|------|------|
| 質問入力・回答表示 | 質問を入力し、生成された回答を表示 |
| 出典の提示 | 回答の下に参照したファイル名・ページを一覧表示 |
| 検索結果の確認（任意） | 取得チャンクとスコアを開いて確認できる（デバッグ/透明性） |
| 処理時間・トークン表示（任意） | 応答時間や使用トークンの簡易表示 |

UIは Alpine.js（ビルド工程なし）。Express が静的ファイルとして配信し、ブラウザから /api/ask 等を叩く。管理機能（文書追加・再索引）は初期はコマンド実行とし、UI化は将来。

## 5. 非機能要件

| 項目 | 要件 |
|------|------|
| ハルシネーション抑止 | 検索結果の範囲内で回答するよう指示。出典必須 |
| プライバシー | PDF全文はローカル保持。APIには質問＋検索断片のみ送信 |
| 動作環境 | Raspberry Pi 4（RAM 4GB）、64bit Raspberry Pi OS、Node.js LTS |
| メモリ | 埋め込みモデル（量子化）＋Nodeで実メモリ概ね1GB前後。4GBで余裕 |
| 応答性 | 低トラフィック前提。埋め込みは1クエリ数百ms〜数秒を許容 |
| 可用性 | ラズパイ常時稼働 |
| バックアップ | 文書と索引（JSON）を定期バックアップ（SDカード破損対策） |
| 保守性 | Node 単一ランタイム。ビルド工程を最小化し、依存を必要最小限に |

### 5.1 セキュリティ（学外公開に伴い必須）

外部からアクセス可能にするため、以下を設計段階から織り込む。

| 項目 | 要件 |
|------|------|
| 認証 | 利用者の認証（最低限の合言葉/トークン、将来はサークル認証連携） |
| 通信の暗号化 | TLS(HTTPS)。Tunnel側で終端する構成を想定 |
| APIキー保護 | Gemini APIキーはサーバー内のみ保持。ブラウザに出さない |
| レート制限 | 1IP/1セッションあたりの呼び出し上限。乱用・コスト暴発の防止 |
| 入力検証 | 質問長やリクエスト頻度の制限 |

## 6. システム構成

### 6.1 配置

```
┌───────────────────────────────────────────┐
│  利用者（学内外）スマホ/PC ブラウザ           │
└───────────────────────────────────────────┘
                  ↓ HTTPS（Tunnel経由）
┌───────────────────────────────────────────┐
│  ラズパイ（部室内） Node サーバー             │
│  ├─ Web UI（Alpine.js・静的配信）            │
│  ├─ APIサーバー（/api/ask 等・認証/制限）     │
│  ├─ ローカル埋め込み（MiniLM ONNX）          │
│  ├─ ベクトル検索（JSON＋総当りcosine）        │
│  ├─ BM25（形態素＋用語保護層）               │
│  ├─ RRF統合・係名ブースト・用語注入           │
│  ├─ Generator（差し替え可能。今はGemini）     │
│  └─ 文書/索引/辞書データ                     │
└───────────────────────────────────────────┘
                  ↓ HTTPS（生成のみ）
┌───────────────────────────────────────────┐
│  外部API: Gemini（回答生成）                  │
└───────────────────────────────────────────┘
```

### 6.2 技術スタック（案）

| 層 | 技術 | 理由 |
|------|------|------|
| ランタイム | Node.js (LTS) | 単一ランタイム、ラズパイARM対応 |
| Webサーバー | Express | 軽量・定番・学習コスト低 |
| フロントエンド | Alpine.js（ビルド工程なし） | 依存最小・ビルド不要でラズパイ運用に最適 |
| 埋め込み | transformers.js（onnxruntime-node）/ MiniLM多言語・量子化ONNX | ローカル実行・無料・日本語対応 |
| ベクトル検索 | JSON保存＋総当りコサイン（自前） | 数百チャンク規模ではDB不要。Chroma撤廃で保守減 |
| 形態素解析 | kuromoji.js + 用語保護層（自作） | 純JS・ネイティブ依存なし。固有語はユーザー辞書相当の保護層で1語化 |
| BM25 | 自前実装 or 軽量ライブラリ | 小規模ロジック |
| 生成 | Generator抽象（既定: @google/genai Gemini） | 差し替え可能。将来ローカルLLMへ |
| PDF抽出 | pdf-parse / pdfjs-dist | 索引構築時のみ |

Python版との主な違い: Chroma を撤廃（JSON＋総当りcosine）、Janome を kuromoji.js＋用語保護層に置換、sentence-transformers を transformers.js(ONNX) に置換、生成は差し替え可能な Generator に抽象化。残りのロジック（RRF・ブースト・用語注入・整形）は移植。

### 6.3 ユーザー辞書の方式（用語保護層）

形態素解析器は内蔵辞書（IPADIC）で単語境界を決めるため、内蔵辞書に無い固有語（総リー・IB 等）は誤分割される。kuromoji.js は内蔵辞書方式でユーザー辞書追加が手軽でないため、Python版の user_dict.csv に相当する役割を「用語保護層」で代替する。既存の用語リスト（kakari_terms.csv・用語辞典の見出し語）を流用し、トークナイズ前後で固有語を1語として扱うことを保証する。精度をさらに求める場合は WASM形態素解析（Lindera等）への移行を将来オプションとする。

## 7. 制約条件

| 制約 | 詳細 |
|------|------|
| 生成のネット依存 | 回答生成のみ Gemini API（要ネット） |
| 外部公開のセキュリティ | 学外公開のため認証・TLS・キー保護・レート制限が必須 |
| 索引の作り直し | 埋め込みモデルがJS側に変わるため、索引はJS版で再構築（Python版のChroma索引は流用不可） |
| 文書更新 | 手作業で新版に差し替え（自動化は将来） |
| コスト | 基本無料。Gemini無料枠を想定 |

## 8. スコープ（フェーズ分け）

### Phase 1（まず作る）
- 索引構築スクリプト（PDF/MD取り込み→チャンク→ローカル埋め込み→JSON保存）
- 検索コア（ベクトル＋BM25＋RRF＋係名ブースト＋用語注入）
- 生成（Gemini）と出典付き回答（Generator抽象で実装）
- 最小Web UI（Alpine.js：質問→回答→出典）
- 最低限のセキュリティ（認証・キー保護・レート制限・TLS前提）
- 動作確認用のコマンド（検索のみ／質問応答）

### Phase 2（その後）
- 文脈整形のWeb表示最適化、検索結果の詳細表示
- 評価セットによる定量チェックの移植
- 管理UI（文書追加・再索引）
- 認証の本格化（サークル認証連携など）
